# feat(ui): Add the Theme control to the nav

- **Release tag:** `v0.0.161`
- **Source PR:** [#377](https://github.com/mpaulosky/Blazor-Server/pull/377)

## PR description

Closes #364

### Why

The Generated App could already store a visitor's Theme in a `theme` cookie and render it as `data-theme` on <code>&#60;html&#62;</code>, but nothing in the UI let a visitor choose it.
Visitors had no way to pick Light or Dark, or go back to following the OS.
This adds the control for that, in the nav on desktop and in the mobile menu, as `docs/plans/theme-and-palette.md` describes.

### What changed

- New `src/UI/Components/Features/Themes/ThemeControl.razor`, a statically rendered component.
  It renders one <code>&#60;form method&#61;&#34;post&#34; data&#45;enhance&#62;</code> that posts to the base-relative `theme` path, with an antiforgery token and a hidden `returnUrl` holding the current path and query.
- The form is a `role="group"` labelled "Theme". It holds three submit buttons named `theme`, with the values `light`, `dark` and `system` in that order, each with a sun, moon or monitor icon.
  The button for the current Theme, read from the `theme` cookie (System when there's none), has `aria-pressed="true"` and `bg-accent-600`.
  The other two have `aria-pressed="false"`.
- On desktop each button's name is `sr-only`, and the name is also the button's `title`.
  With `Mobile="true"` the names are visible and the form is a `grid grid-cols-3`.
  Every new surface has `dark:` variants and uses only `accent-*` for accent colour.
- `src/UI/Components/Layout/NavMenu.razor`: <code>&#60;ThemeControl&#47;&#62;</code> comes after `LoginDisplay` in the desktop <code>&#60;nav&#62;</code>, replacing the comment that marked its place.
  The <code>&#60;details&#62;</code> menu gets a bordered `div` after `LoginDisplay` that holds <code>&#60;ThemeControl Mobile&#61;&#34;true&#34;&#47;&#62;</code>.
- `README.md` describes the Theme as built and drops it from the Roadmap.
- There was no design note for this issue. The control follows the plan's class lists and markup.

### Verification

- `tests/UI.Tests.Unit/Components/Features/Themes/ThemeControlTests.cs` (bUnit) covers:
  - the single form, with its `post` method, `data-enhance`, the `theme` action, the antiforgery token and the `returnUrl` path and query
  - the group role and the "Theme" label
  - the three buttons' names, values and order, and their accessible names Light, Dark and System
  - which button is pressed and accented with no cookie, with `light`, with `dark` and with an unknown value
  - the `sr-only` names on desktop, and the visible names and `grid grid-cols-3` form with `Mobile`
- `tests/UI.Tests.Unit/Components/Layout/NavMenuTests.cs` checks that exactly one Theme form renders in the desktop <code>&#60;nav&#62;</code> without the mobile layout, and exactly one in the <code>&#60;details&#62;</code> menu with it.
  The tester's first version of these two tests looked the control up through bUnit's <code>FindComponents&#60;ThemeControl&#62;&#40;&#41;</code>.
  bUnit parses each component found that way into a separate document, so the nav could never contain it, whatever the control rendered.
  The tests now look for the form inside the rendered nav and menu, and still require exactly one in each.
- `tests/UI.Tests.E2E/ThemeTests.cs` (Playwright, through the AppHost) checks that choosing Dark sets `data-theme="dark"` on <code>&#60;html&#62;</code> and that it's still there after a reload.
  It also checks that choosing System afterwards removes the attribute.
- `scripts/gate.sh` passed on the final branch: lint, the Release build, and every test project.
  That's 230 unit, 78 integration, 30 Domain, 5 AppHost and 25 architecture tests, plus the E2E project with 9 passed and 1 skipped (the existing Auth0 login test).
