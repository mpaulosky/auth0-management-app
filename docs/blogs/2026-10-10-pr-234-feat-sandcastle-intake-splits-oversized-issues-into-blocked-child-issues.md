# feat(sandcastle): Intake splits oversized issues into blocked child issues

- **Release tag:** `v0.0.110`
- **Source PR:** [#234](https://github.com/mpaulosky/Blazor-Server/pull/234)

## PR description

Closes #75

### Why

Intake (#74) can only mark an issue ready or hand it back. An issue that's clear but too big for one PR either gets
built as one oversized change, or sits waiting for a person to split it. #75 lets intake split such an issue into
child issues built in order, each with a share of the original's acceptance criteria. The original becomes an
umbrella that closes once all its children are done. Spec: "Phase 2: Intake" in `docs/plans/sandcastle-workflow.md`.

### What changed

- **Split verdict** (`intake-prompt.md`, `lib/intake.mts`): intake can answer `split` with <code>children&#58; &#91;&#123; title&#44; body &#125;&#93;</code>
  in build order.
  - The prompt says to split only an issue that already meets the Definition of Ready, only when its criteria fall
    into separately shippable parts, and to redistribute the criteria word for word without adding any.
  - The schema keeps `main`'s lenient `id` and `bug`.
- **Applying a split** (`applySplit`): each child is created with `Sandcastle` (plus `bug` when the verdict says so),
  added as a native sub-issue of the original, and linked as blocked by the child before it. Only then does the
  original lose `Sandcastle` and get a comment carrying <code>&#60;&#33;&#45;&#45; sandcastle&#58;umbrella &#45;&#45;&#62;</code> (`UMBRELLA_MARKER`) that lists
  the children. The children go through intake on their own in the next round.
  - The first child takes over the original's blockers, since the original stops being built once it loses
    `Sandcastle`. They come from native links in this repository (`sameRepoBlockers`) and "Blocked by #N" lines in its
    body. They're read before anything is created, and go in the first child's body as a "Blocked by" line the gate
    reads, so a blocker GitHub won't link can't fail the split partway.
  - The issue gets `sandcastle:needs-human` before the first child is created, and each child is created with it too.
    The label comes off every child, then the original, only once the umbrella comment is posted. So neither a
    concurrent run nor a later round splits the issue twice, and no child is built before the split finishes.
  - Child titles and bodies are model text posted from the host's account, so `withoutReferences` breaks mentions,
    `#N` and `GH-N` references, `github.com` links and character references in their prose. Code spans and fenced
    blocks, found as CommonMark finds them, stay as written, so Razor directives such as `@page` reach the agent intact.
    The CommonMark rules: no span after an escaped backtick or across a block, and no backtick fence with a backtick in
    its info string.
- **A malformed split:** no children, a child with a blank title, or a child with no acceptance criteria. Nothing is
  created, and the issue is handed back with `sandcastle:needs-info` and a question asking a person to split or
  narrow it.
- **A split that fails:**
  - If adding the mark fails, nothing has been created, and the issue stays unjudged. The mark is taken back off in
    case GitHub added it anyway.
  - Any later failure hands the issue back with `sandcastle:needs-human`, even before the first child exists: GitHub
    may have created a child despite answering with an error.
  - The comment lists the children created, which stay held, and names one a failed create may have made. Its recovery
    steps depend on how far the split got. To re-queue the original, close the sub-issues as not planned, so the
    umbrella check can't close it as completed, and add `Sandcastle` back if the split had removed it.
  - A hand-back that fails too is only logged: the mark already keeps the issue out of intake.
- **Umbrellas** (`lib/umbrella.mts`, Phase 0 in `main.mts`): each round, before intake, the host closes as completed
  every open umbrella whose sub-issues have all closed as completed.
  - An umbrella with no children yet stays open, and so does one with any child still open or closed as not planned.
  - An umbrella carrying `Sandcastle` or `sandcastle:needs-human` stays open too. That covers one that was handed
    back, or re-queued after a split failed once its umbrella comment had already landed.
  - The host finds umbrellas through GitHub search (`openIssuesWithComment`), keeping only issues where the host itself
    posted the marker, so a pasted marker can't get an issue closed.
  - A failure is logged and checked again next round.
- **GitHub helpers** (`lib/github.mts`): `createIssue` (REST, with labels), `addSubIssue`, `subIssuesOf`,
  `closeIssueAsCompleted` and `openIssuesWithComment`.
- **Merge with `main`** (#225, #229): `handBackComment`, shared by the needs-info and malformed-split comments, posts the
  reason through `plainText`. The umbrella, partial-split and malformed-split comments now pass the reason and the child
  titles through `plainText` too, so #224's guarantee covers split verdicts. `plainText` shares `breakReferences` with
  `withoutReferences`.

### Verification

- `intake.test.mts`:
  - A well-formed split creates a sub-issue for each child in build order, each blocked by the one before it, adds
    `bug` when asked, and only then removes `Sandcastle` and posts the umbrella comment.
  - A split with no children, a blank title, or a missing or empty acceptance-criteria section is handed back with
    `needs-info`.
  - The issue is marked before the first child is created and unmarked after the umbrella comment. A failed mark leaves
    it unjudged with nothing created.
  - A failed first create, a failure partway, and a failed hand-back all keep the issue out of intake. The recovery
    steps match how far the split got.
  - Children are created with no working mention or reference in their prose. Their Markdown, and their code spans
    and fences (`@page`, `@inject`), are kept as written. A malformed split's child title is posted as plain text.
  - The first child's body names the original's native and body blockers, and a failed read of them leaves the issue
    unjudged with nothing created. Children are created held, and are released only after the umbrella comment is
    posted, never after a partial failure.
  - A mention after an escaped backtick, between a stray backtick and a later span, or after a fence opener with a
    backtick in its info string is still broken.
  - A failed mark is taken back off, and a failure to do that is logged. The recovery steps say "not planned".
  - I checked each new test by removing the code it covers and confirming it turns red.
  - The schema accepts a split, and rejects a child with no body.
  - The hostile-text tests now cover the umbrella comment's reason and its child titles. Removing `plainText` there
    turns them red.
- `umbrella.test.mts`:
  - An umbrella carrying `Sandcastle` or `sandcastle:needs-human` stays open, and the log says why.
  - An umbrella closes once every child has closed as completed.
  - It stays open with a child still open, a child closed as not planned, or no children yet.
  - Finished umbrellas still close when another umbrella's check fails, and `umbrellaPhase` logs a failure rather
    than ending the run.
- `github.test.mts` covers each new helper's gh calls, and checks that `sameRepoBlockers` leaves out other
  repositories' blockers. That includes adding a sub-issue by the child's id rather than
  its number, and only counting umbrella comments the host posted.
- `main.test.mts` checks that the umbrella phase runs each round, before intake.
- `pnpm run check:sandcastle` passes (498 tests), and so does `scripts/gate.sh` on push.
- The tests stub `gh`, so the sub-issue and dependency API calls haven't been run against GitHub yet. The first real
  split will exercise them.
