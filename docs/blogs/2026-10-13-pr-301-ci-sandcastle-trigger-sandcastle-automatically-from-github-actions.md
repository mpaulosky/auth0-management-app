# ci(sandcastle): Trigger Sandcastle automatically from GitHub Actions

- **Release tag:** `v0.0.138`
- **Source PR:** [#301](https://github.com/mpaulosky/Blazor-Server/pull/301)

## PR description

### Why

Sandcastle runs only when someone starts `.sandcastle/main.mts` by hand. Intake, follow-up, giving up and the run controls are now in place, so it can run unattended. Sandcastle's PAT has no Workflows permission (ADR 0002), so this workflow has to be added by hand.

### What changed

- **`.github/workflows/sandcastle.yml`** runs on `ubuntu-24.04`. It starts on:
  - the owner adding `Sandcastle`;
  - the owner removing `sandcastle:needs-info` or `sandcastle:needs-human` from an issue or PR;
  - Copilot reviewing a PR, or `Build and Test Suite` finishing, on a same-repo `feature/`, `fix/` or `hotfix/` branch;
  - `workflow_dispatch` from `main`;
  - a schedule every 2 hours.

  The job's `if:` does all the filtering, so any other event ends as a skipped job. The concurrency group (`sandcastle`, no cancel) and `timeout-minutes: 350` are on the job, and the workflow's `GITHUB_TOKEN` is `contents: read`.
- **Steps:**
  1. Check the secrets.
  2. Check out `main` with `persist-credentials: false`.
  3. Install the `dotnet-*` skills.
  4. Run `gh auth setup-git`.
  5. Set up pnpm and Node 22, then run `pnpm install --frozen-lockfile`.
  6. Run `pnpm run sandcastle`.
  7. Upload the run report (`summary.md` and `handbacks.json`), always, kept for 14 days. The role transcripts stay on the runner: a public repo's artifacts can be downloaded by any signed-in user, and a transcript could hold the Claude token.
  8. Fail the job when `handbacks.json` lists any hand-back.
- **Three things the issue didn't list, all needed on a hosted runner:**
  - The library passes only the keys named in `.sandcastle/.env` into the sandbox, and that file is git-ignored. The run step writes it with the chosen Claude key and no value, so the token is read from the job's environment and never written to disk.
  - Sandcastle copies the host's git `user.name` and `user.email` into the sandbox for the agents' commits. The runner has neither, so the workflow sets the PAT owner's login and no-reply address.
  - `upload-artifact` skips hidden paths by default, so the report under `.sandcastle/logs/` needs `include-hidden-files: true`.
- **Skills:** the workflow fetches `Support For New Projects/.claude/skills` from the owner's public `dotfiles` repo at a pinned commit, without a token and before the credential helper exists, and links it to `~/.claude/skills`. Hosted runs therefore mount all six skills, and the step fails if the pinned commit lacks one. A push to `dotfiles` changes nothing here until the pin moves.
- **Spec** (`docs/plans/sandcastle-workflow.md`): records the `.env`, git identity and skills setup. It also records who gets the failure email, based on the users GitHub attributed recent runs to:
  - CI-triggered runs: always the owner.
  - Copilot-review runs: the owner in 96 of 100 runs, and `Copilot` in 4. A run attributed to `Copilot` emails no one.

### Verification

- `yamllint`, `actionlint` and `zizmor` (v1.30.1) pass on the workflow, and `markdownlint` passes on the spec.
- `scripts/gate.sh` passed through the pre-push hook.
- Not yet checked on a live run, because it can't be before merge: that a skipped event never displaces a pending run, that the PAT can push, that the log has no missing-skills warning, and that a hand-back turns the run red. Check these with a `workflow_dispatch` from `main` after merge.
