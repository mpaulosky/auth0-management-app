# feat(ManagementApi): Cache Management API reads

- **Release tag:** `v0.0.18`
- **Source PR:** [#56](https://github.com/mpaulosky/auth0-management-app/pull/56)

## PR description

Closes #34

### Why

The Users and Roles pages will call Auth0's Management API through `IManagementApi`, and Auth0 rate-limits that API.
Without a cache, an Admin paging back and forth through a User list, or reopening the same User or Role, sends the same read to Auth0 every time and uses up the rate limit for no reason.
Once reads are cached, a write has to clear the entries it makes stale, or an Admin would see old data right after their own change.

### What changed

- `CachedManagementApi` (internal, sealed, in `src/UI/ManagementApi/`) wraps the adapter. It caches only successful `Result`s in its own `MemoryCache`, with `SizeLimit = 1000` and size 1 per entry:
  - a search page, keyed on the trimmed lower-case query, the page and the page size, for 30 s
  - one User, by id, for 60 s
  - the Role list for 5 min
  - a Role's members, by Role id, for 60 s
- Each entry stores its expiry time, taken from the injected `TimeProvider`, and that time decides whether the entry is still fresh.
  The same lifetime goes on the `MemoryCache` entry only so the memory gets freed.
- A failure, a 429 included, is never cached. `CountRoleMembersAsync`, `UserHoldsRoleAsync` and every write always go to Auth0.
- Writes clear the entries they make stale. They do this even when the write fails or throws, because it may still have reached Auth0:
  - `UpdateProfileFieldsAsync` clears that User, every search page and every Role's members, because those rows show the User's name, email and picture.
  - `AssignRoleAsync` and `RemoveRoleAsync` clear that User and that Role's members.
  - `CreateRoleAsync` clears the Role list.
- The search pages and the Role-member entries each form an eviction group that shares one change token, so a write drops the whole group at once.
  A read takes the group's token before it calls Auth0, so a write that lands while the read is in flight leaves the new entry already expired.
- `AddManagementApi()` now registers the adapter as its own singleton and `IManagementApi` as the `CachedManagementApi` wrapping it.
  Both use `TryAdd`, so they're registered once even when `AddManagementApi()` runs twice.
- `CLAUDE.md` describes the cache as part of the Management API seam.

The branch follows the cache and registration sections of `docs/plans/user-role-management.md`. Issue #34 had no separate design note.

### Verification

- `tests/UI.Tests.Unit/ManagementApi/CachedManagementApiTests.cs` goes through `AddManagementApi()` with the stub Auth0 handler and a `FakeTimeProvider`. It pins:
  - that `IManagementApi` resolves to the one singleton `CachedManagementApi`, and still caches when registered twice
  - that 1,000 distinct pages all stay cached and the 1,001st is refused
  - that a 429 or a catalogued error isn't cached
  - each entry's lifetime, both just inside it and just past it, and that each entry expires on its own clock
  - the cache keys
  - that counts, role checks and writes always reach Auth0
  - which entries each successful write clears
  - that a write which fails with a 429 still clears its entries (`Write_FailsWith429_StillEvictsTheEntriesItMakesStale`, added in review)
- `tests/Architecture.Tests/ManagementApiTests.cs` checks that `CachedManagementApi` is internal and sealed and implements `IManagementApi`.
- `scripts/gate.sh` passed on the final commit: lint, the Release build and every test project. It ran 596 UI unit tests. One E2E test, which needs Auth0 settings this run didn't have, was skipped.
