# feat(sandcastle): Stop unattended runs cleanly when there's no work, time or usage left

- **Release tag:** `v0.0.113`
- **Source PR:** [#241](https://github.com/mpaulosky/Blazor-Server/pull/241)

## PR description

Closes #147

### Why

Before a workflow can start Sandcastle on its own, a run has to meet four conditions:

- it's cheap when there's nothing to do;
- it stops inside the Actions job limit;
- it stops cleanly at Claude's usage limit;
- it hands back work that needs a workflow-file change instead of retrying it.

Until now, Sandcastle had none of these. It always ran a full round, ran until `MAX_ITERATIONS`, counted a usage-limit stop as a failed build (so two of them handed the issue back), and retried a push GitHub would never accept.

Split from #80. It builds on #146's queue scope and #77's sweep. Spec: `docs/plans/sandcastle-workflow.md`, "The round", "Giving up and telling the human" and "Trigger and run environment".

### What changed

**Early exit (`lib/work.mts`, new).**

- After the sweep and the umbrella check, and before intake (the first step that can start Claude) or any sandbox, `findWork` looks for one of these, checked in this order:
  - a PR the sweep flagged as needing a follow-up pass;
  - an in-scope issue intake would judge, using intake's own `needsIntake` filter, so an issue being built or with an open PR doesn't count;
  - a ready, unblocked issue from the gate.
- With none, the run logs "Nothing to do in …" and exits 0.
- The gate's blocker lookups run only when nothing earlier was found.
- `followUpPhase` now returns the PRs that need a pass. A failed sweep returns none, so it never counts as work.
- The retry of stale `sandcastle:building` labels moved ahead of this check, so a stale label doesn't hide an issue from it.

**Time budget (`lib/limits.mts`, new; `lib/config.mts`).**

- `SANDCASTLE_BUDGET_MINUTES` defaults to 240, against the job's 350-minute timeout. It's read at startup, and the clock starts there.
- A value that isn't a positive whole number exits 2 with the reason.
- Once the budget has passed, no new round starts (checked at the top of each round) and no role run starts (`runWithinLimits`).
- A publish that's already been reached still goes ahead, since it costs seconds and no usage.

**Usage limit.**

- `isUsageLimitError` and `usageLimitLine` look for Claude Code's usage-limit and rate-limit wording at the start of a plain line (its stderr or result text) or of a stream-json `result` event's text. Tool results and the agent's own text never count, because Sandcastle works on this very file. They read the error's message and up to 5 levels of its `cause` chain, since Sandcastle wraps errors through Effect.
- A 529 or `overloaded_error` is a server overload, not a usage limit, and stays a counted failure.
- When a role run hits the limit, the stop is recorded and it throws `UncountedStopError`. From then on, no role starts.
- A build whose roles have all finished still publishes. Publishing costs no usage and starts no Claude review, and an ephemeral runner would lose unpushed work. The issue's "publish nothing more" is read as "nothing unfinished".
- `main.mts` catches the stop around the round loop and ends the run cleanly with exit 0.
- The critique rethrows the stop instead of treating it as a failed critique.
- The round summary names a stopped build with a ⏹ line, and an uncounted stop isn't logged as an agent failure. The line says the attempt's unpushed commits are dropped with an ephemeral runner's checkout and the next run rebuilds the issue.

**Workflow-file pushes (`lib/build.mts`, `lib/handback.mts`).**

- `isWorkflowPushRejection` matches GitHub's "refusing to allow a Personal Access Token / an OAuth App / a GitHub App to create or update workflow" rejection. It reads only the command's output, not the command line, which could name a workflow branch.
- Such a push hands the issue back with `sandcastle:needs-human`. The comment explains:
  - Sandcastle's token has no Workflows permission;
  - GitHub doesn't have the attempt's commits, naming the refused head and each workflow file the branch's commits touch. The files come from `git log --name-only` over the branch side, so an edit a later commit reverted (which GitHub still refuses) is listed and files main changed aren't. Each name sits in a code span it can't break out of, because the names come from the agent's commits and the comment is public;
  - to re-queue, make the workflow change in its own PR, then remove the label once it has merged.
- The hand-back isn't counted as a failed build. If the hand-back itself fails, the build still resolves.

`.sandcastle/.env.example` documents `SANDCASTLE_BUDGET_MINUTES`.

### Verification

- `pnpm run check:sandcastle` passes (803 tests), with these new ones:
  - `limits.test.mts`: the budget boundaries with an injected clock (no budget before `start()`, just short, exactly at), which stop wins when both apply, and every usage-limit wording. It also covers case, a nested `cause`, a stream-json line and 5-deep chains, and confirms that an overload, an abort, a test failure and a failed hook don't match.
  - `work.test.mts`: no work when every issue is handed back, being built, has an open PR or is held by the gate. Work is found for an unjudged issue (without calling the gate), for a PR needing a pass, and for a ready issue.
  - `build.test.mts`: a usage-limit stop records no failed attempt, posts no comment and publishes nothing, including when another build hit the limit after this one's reviewer finished. A workflow-push rejection hands the issue back, and the match covers each token type while rejecting non-fast-forward, server-error and command-line-only text.
  - `agents.test.mts`, `critique.test.mts`, `round.test.mts`, `follow-up.test.mts`, `handback.test.mts`: the role runner's limit checks, the critique's rethrow, the ⏹ summary line, the sweep's `needsPass` and the hand-back comment.
  - `main.test.mts`: the order in `main.mts`. The budget is read before `protectHostGit()`; the limits are checked at the top of each round; the work check comes after the umbrellas and before intake; and the round loop catches `UncountedStopError`.
- Review fixes, each test-first and mutation-checked:
  - quoted phrasings in tool or agent output aren't a usage limit;
  - finished work still publishes after another build hits the limit;
  - the workflow hand-back names the files and head and no longer points at a branch GitHub refused;
  - the workflow files come from the branch's commits, so files main changed and reverted edits are handled correctly;
  - a file name with a backtick can't break out of its code span;
  - the ⏹ line no longer claims unpushed commits survive.
- The usage-limit wording is matched against Claude Code's current output, which can change between versions. The patterns are kept in one list (`USAGE_LIMIT_PATTERNS`) so they're easy to update.
