# feat(sandcastle): Show why each Sandcastle PR is held

- **Release tag:** `v0.0.26`
- **Source PR:** [#79](https://github.com/mpaulosky/auth0-management-app/pull/79)

## PR description

Closes #65

### Why

Nothing showed why Sandcastle was holding one of its pull requests.
The follow-up pass count, the open review threads, the branch state and the hand-back label each lived in a different place.
Working out why a PR hadn't merged took several `gh` calls and a read of `.sandcastle/lib/follow-up.mts`.
On 2026-10-20, for example, PRs #56 and #59 had each used 2 of their 3 follow-up passes, and the only way to see that was to read their follow-up comments one by one.
#59 was also behind `main`, and nothing said the sweep was leaving it there on purpose until its bot threads were answered.
This affects anyone who runs Sandcastle and needs to know why a PR is held.

### What changed

- `pnpm run sandcastle:status` (a new root `package.json` script) runs `.sandcastle/status.mts`.
  The script pins host git with `protectHostGit()` before its first `gh` call, always uses the default Sandcastle label scope, and exits with the status command's exit code.
- The new `lib/status.mts` lists each open Sandcastle PR into `main`: the host's own PRs and the ones labelled `sandcastle:follow-up`. Each entry gives:
  - the PR's number, title and issue, and its URL;
  - its follow-up passes used, as `N of 3`. They're counted with `markerCommentsSince` from the same reads the pass counts from, so a PR that was handed back and picked up again shows its new count;
  - why it's held. That's the sweep's own answer, from `sweepContext`, `admitToSweep`, `sweepSkipReason` and `decide`. The entry also says when the next pass would hand the PR back because its passes are used up;
  - its unresolved review threads, split into bot, owner and other people's threads. Threads whose author couldn't be checked, and threads Sandcastle already answered, appear only when there are some;
  - its merge state, which notes when a `BEHIND` PR is left behind on purpose. Also its checks, and whether it has `sandcastle:needs-human` and `review:claude`.
- The output starts with the Sandcastle workflow's run in progress and its queued runs, or says there are none, and ends with a count of the other open PRs into `main`.
  If one PR's reads fail, that PR gets an error entry in place of its status. If the runs can't be read, an error shows in their place. Either way the other entries still print and the command exits 1.
- `lib/follow-up.mts`: the checks `sweepPullRequests` made before `decide` move into `sweepContext` and `admitToSweep`, which only read. The sweep's behaviour is unchanged and its existing tests pass unedited.
  `NEEDS_HUMAN` and `answeredByHost` are now exported, and `SweepPullRequest` gains `title`.
- `lib/github.mts`: `markerCommentReads` takes the raw reads out of `markerComments`.
  The new `sandcastleWorkflowRuns` runs one `gh run list` for each status a run has before it completes. It merges the results, drops duplicates and sorts them oldest first, and throws on an answer of the wrong shape.
  The sweep's PR query now reads `title`.
- The command is read-only.
  The sweep reads its in-scope issues through `loadQueue`, which writes label fixes. The status calls it through `withoutLabelWrites`, which turns those writes into no-ops, and drops its log so the output doesn't describe writes that never happened.
- `CLAUDE.md`'s Commands block and `docs/plans/sandcastle-workflow.md` (a **Status** paragraph in Phase 1, and `status.mts` in the module layout) list the command.
- Departures from the design note:
  - The restore wording reads "the next sweep puts <code>&#60;label&#62;</code> back (<code>&#60;reason&#62;</code>)", because the reason itself starts with "put back".
  - Each entry also shows the PR's URL and marks a hand-off PR.
- Limitations:
  - The hand-back forecast applies the rule the issue asks for: the PR needs a pass and has used all its passes. The pass itself reads fresh threads and checks first, and it can still skip a PR that needs one, such as a PR held only by owner threads. In that case the status says more than the pass will do.
  - GitHub's run list has no issue field, so each run shows its event and display title rather than an issue number.

No new dependency was added, so `pnpm-lock.yaml` is unchanged.

### Verification

- `.sandcastle/lib/status.test.mts` (new) pins:
  - which PRs are listed and how other open PRs are counted;
  - the pass count since `sandcastle:needs-human` was last removed. Strangers' markers and hand-back comments aren't counted;
  - the reason a PR is held, compared against `decide` or `sweepSkipReason` for each case the issue names: merge conflicts, running and red checks, bot and owner threads, Copilot's review pending or missing, only behind main, labelled `sandcastle:needs-human`, settled, a stranger's hand-off label, and a stranger removing `sandcastle:needs-human`;
  - when the next pass hands a PR back;
  - the thread split, the runs block, per-PR and runs read failures, and the exit codes;
  - that nothing writes: the stub host's write members throw and an `afterEach` check fails on any of them. `withoutLabelWrites` and `loadQueue` are checked too, and a source check confirms the module imports no GitHub write.
- `.sandcastle/status.test.mts` (new) pins the `package.json` script, the `CLAUDE.md` and plan entries, and that `status.mts` calls `protectHostGit()` first and sets the default label scope.
- `.sandcastle/lib/follow-up.test.mts` adds tests for `sweepContext` (the values it computes and its read order) and for `admitToSweep` (each skip, approval and restore case, and reading events once).
- `.sandcastle/lib/github.test.mts` adds tests for `markerCommentReads`'s `gh` calls, `sandcastleWorkflowRuns` (its calls, merging, sorting and fail-closed parsing) and reading `title`.
- `pnpm run check:sandcastle` passes (1646 tests), and `scripts/gate.sh` passes: the Markdown lint, the Sandcastle check, the Release build and every test project.
