# fix(sandcastle): Keep comments from anyone with write access, not only the repository owner's

- **Release tag:** `v0.0.103`
- **Source PR:** [#218](https://github.com/mpaulosky/Blazor-Server/pull/218)

## PR description

### Why

`ownerApproved` (`.sandcastle/lib/github.mts`) kept only the issue comments whose author was the repository owner, the
owner part of `owner/repo`. Text from anyone else never reached a role's prompt. That's right for a repository a
person owns. But when an organization owns the repository, the owner is the organization, and an organization never
posts comments. Every comment was dropped, so the maintainers' guidance on an issue never reached the agents. This
template is meant to be copied, and a copy can belong to an organization (#214).

PR #213 fixed the same assumption in the marker-comment count by using the login `gh` is signed in as. That fix doesn't
fit here. This filter decides whose guidance the agents trust, not which comments the host posted, so it should keep the
comments of anyone who can push to the repository.

### What changed

- **Trust comes from write access, not the owner's login.** `ownerApproved` now keeps a comment when its author has
  `admin`, `maintain` or `write` permission. It reads that from <code>GET repos&#47;&#123;repo&#125;&#47;collaborators&#47;&#123;login&#125;&#47;permission</code>.
  GitHub reports `maintain` as `write` in `.permission` and names it only in `.role_name`, so either field counts.
- **The filter fails closed.** A lookup that fails, or an answer with neither permission field, drops that author's
  comments, so an error never lets a stranger's text through. The failure is logged with the author and `gh`'s error.
- **Some 404s are a definite "no".** gh prints <code>&#60;login&#62; is not a user &#40;HTTP 404&#41;</code> for a login GitHub doesn't know, such
  as the bare `github-actions` it shows for a GitHub App's comment. That's cached as no access and not logged. Any
  other 404, such as a token that can't see the repository, is a failed lookup.
- **Each author is looked up once per run.** `listSandcastleIssues` passes a map that lives for the whole process, so an
  author who comments on several issues, or on the same issue across rounds, is looked up once. Only GitHub's answer is
  cached, never a failure: one transient error, such as a 502 or a rate limit, would otherwise drop a maintainer's
  guidance for the rest of the run.
- **A failed lookup waits for the next round.** Within a round, an author whose lookup failed has their comments dropped
  without another lookup or warning, because a retry in the same burst would most likely fail too and deepen a rate
  limit. `listSandcastleIssues` starts a fresh set of failures on each call, so the author is retried next round.
- **Revoking access takes effect on the next run.** Because answers are cached for the whole run, a permission granted
  or revoked partway through a run takes effect in the next run. To cut someone off at once, stop the run. The code
  comment and the plan say so.
- **`gh` can be stubbed.** `ownerApproved` and `listSandcastleIssues` take `repo`, `run: typeof execFileSync` and the
  cache as parameters with live defaults, as `ensureLabels` and `handBack` do. `warn` takes the failure log and `failed` the round's failed lookups. `repoOwner()` had no other caller, so it's removed.
- **Comments and plan updated.** The comments on `SandcastleIssue`, `ownerApproved`, `listSandcastleIssues` and the
  `prompts.mts` header now say "authors with write access". So do the Principles and Labels sections of
  `docs/plans/sandcastle-workflow.md`.
- **`prompts.test.mts` no longer filters comments itself.** It now starts from an already-filtered `SandcastleIssue`,
  and the filter is tested where it lives, in `github.test.mts`.

The function keeps its name `ownerApproved`. The issue didn't ask for a rename, and none of its callers changed.

### Verification

Tests in `.sandcastle/lib/github.test.mts` (`describe("ownerApproved")`) run against a stubbed `gh`:

- `keeps a comment from an author with write permission`
- `keeps a comment from an admin`
- `drops a comment from an author with only read permission, or none`
- `keeps a maintainer's comment in an organization-owned repository`: the author isn't the owner and reports
  `role_name: maintain`.
- `keeps a comment when only permission grants write access` (a custom role) and `keeps a comment when only role_name
  grants write access`: each field is enough on its own.
- `drops a comment whose permission lookup fails`, `drops a comment whose permission lookup prints something other than
  JSON` and `drops a comment whose permission lookup has neither field`.
- `describe("an author GitHub doesn't know (HTTP 404)")`, using gh's real `github-actions is not a user (HTTP 404)` text:
  the comment is dropped, the author is looked up once across two issues, and nothing is logged. In the same block,
  `treats a 404 that isn't about the login as a failed lookup: reported and not cached`.
- `describe("a lookup that failed in this round")`: one lookup and one warning for two comments on one issue, and one
  lookup across two issues sharing the round's set.
- `looks an author up again in a later round after a lookup that failed`: a 502 then a success, sharing one map, means
  two lookups and the comment kept the second time.
- `reports a permission lookup that failed, naming the author`.
- `looks an author up once for several comments on one issue` and `looks up an author once across issues that share a
  cache`.
- `describe("listSandcastleIssues")`, which tests the run and round wiring: `looks an author up once across the rounds
  of a run`, `looks an author whose lookup failed up once in a round, across its issues` and `looks an author whose
  lookup failed up again in the next round`.

I checked that the tests go red when the code they guard is broken: checking only one of the two permission fields,
letting a JSON parse error escape, trusting an answer with no fields, caching a failure, treating every 404 as "no
access", dropping the round's set of failures, and giving each round a fresh cache. `pnpm run check:sandcastle`
passes (270 tests).

Sandcastle's gate ran `scripts/gate.sh`, including `pnpm run check:sandcastle`, at both checkpoints.
