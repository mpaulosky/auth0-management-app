# feat(sandcastle): Intake judges each issue against the Definition of Ready

- **Release tag:** `v0.0.105`
- **Source PR:** [#222](https://github.com/mpaulosky/Blazor-Server/pull/222)

## PR description

### Why

Sandcastle built whatever carried the `Sandcastle` label, even when the issue was unclear, so the tester and backend
developer had to guess at what was wanted. This PR adds an intake step before the blocker gate. It judges each new
issue against the Definition of Ready, and either marks the issue `sandcastle:ready` or hands it back to its author
with numbered questions (#74). The spec is in `docs/plans/sandcastle-workflow.md`, under "Phase 2: Intake" and
"Phase 3: Blocker gate".

### What changed

- **The intake prompt.** `.sandcastle/intake-prompt.md` states the Definition of Ready:
  - a Summary of what changes and why;
  - at least one acceptance criterion that can be checked as true or false;
  - no open question that needs a human decision.

  Intake never invents any of these, never edits the issue, and doesn't judge size or worth. It also decides whether
  the issue is a bug, which gives it a `fix/` branch. It answers in an <code>&#60;intake&#62;</code> JSON block, which a zod schema checks.
- **Who gets judged.** Each round, before the gate, `intakeRound` (`lib/intake.mts`) runs intake once over every open
  Sandcastle issue that carries none of `sandcastle:ready`, `sandcastle:needs-info` and `sandcastle:needs-human`.
  Blocked issues are included, so a person sees intake's questions while a blocker is still in flight. Issues another
  run is building (`sandcastle:building`), or whose PR is open, are left out: their work is already done or under way.
  When nothing needs judging, intake doesn't run.
- **How verdicts are applied.** `applyVerdicts` posts one comment per verdict, saying what the host did and why:
  - `ready` adds `sandcastle:ready`, plus `bug` when the verdict says so, in one edit, then posts its comment. A failed
    edit posts nothing, so the next round's re-judgment can't leave a second comment. A rejected comment is logged, and
    the labels stay.
  - `needs-info` adds `bug` first when the verdict says so, then hands the issue back through `handBack`. The issue keeps
    `Sandcastle`, gets `sandcastle:needs-info` and a comment with the numbered questions, and is added to the run's
    hand-back list. The questions go up before the label, so the author always has something to answer. The comment
    says to edit the issue and then remove the label to re-queue it, or to ask a maintainer to if the author can't
    remove labels.
  - The questions are cleaned up before they're numbered: trimmed, kept to one line each, with any numbering intake
    added itself (a number, `.` or `)`, then a space) removed and blank ones dropped. A `needs-info` verdict left with no questions counts as no verdict, so
    the issue is judged again next round.
  - Just before applying a verdict, the host reads the issue's labels again. If another Sandcastle run has judged the
    issue since this round read the queue, the verdict is skipped, so the issue doesn't get two conflicting comments.
  - Verdicts for ids that weren't sent, a second verdict for the same issue, and issues left without a verdict are each
    logged and otherwise ignored.
  - A failed `gh` call before the labels land leaves the issue unjudged. Intake judges it again in a later round, or on
    the next run when nothing else is ready, since the run then ends after the gate. The logs say "a later round or
    run".
- **The gate holds back unjudged and handed-back issues.** `readinessReason` (`lib/gate.mts`) holds back an issue
  labelled `sandcastle:needs-human` or `sandcastle:needs-info`, or one without `sandcastle:ready`, and names the reason
  in the held-back log line. It runs before the issue's blockers are looked up.
- **`hasLabel`, and `addIssueLabel` with several labels.** A case-insensitive label check in `lib/github.mts`, now
  shared by the gate and intake, including the existing `sandcastle:building` check. `addIssueLabel` also takes several
  labels and adds them in one edit.
- **The `bug` label is created at startup.** Intake adds `bug`, and adding a label fails if the repository has deleted
  it. `bug` is now in `SANDCASTLE_LABELS` with GitHub's default colour and description, so `ensureLabels` recreates it.
  `sandcastle:ready` and `sandcastle:needs-info` were already there.
- **Wiring.** `main.mts` runs intake as Phase 0a, before the gate, through `intakePhase` (`lib/intake.mts`). That
  loads the queue and the open PRs, and runs intake over them. A failure, whether loading or judging, is logged and
  costs only the issues intake was judging this round: they lack `sandcastle:ready`, so the gate holds them back, and
  issues already ready can still be built. An `UncountedStopError` still stops the run. The live intake run is built by
  `intakeRunner`, which takes Sandcastle's `runRole` and sandbox so tests can stub them.

#### What changes once this merges

No open issue carries `sandcastle:ready` yet. So the first run after this merges starts with an intake run over every
queued issue that isn't already built or being built. Issues it judges ready are built as before. Issues it hands back with `sandcastle:needs-info` wait until
someone answers the questions, edits the issue and removes the label.

### Verification

New tests, by acceptance criterion:

- **Only unjudged issues are sent to intake**, in `intake.test.mts` (`needsIntake`) and `prompts.test.mts`
  (`intakePromptArgs`):
  - an issue without `sandcastle:ready` is sent, and one with it, `sandcastle:needs-info` or `sandcastle:needs-human`
    isn't;
  - a blocked issue is sent too;
  - the prompt gets only those issues, without anyone else's comments.
- **Applying verdicts**, in `intake.test.mts` (`applyVerdicts`):
  - `adds sandcastle:ready and comments why, for a ready verdict`
  - `leaves a needs-info verdict with Sandcastle and sandcastle:needs-info, a comment of numbered questions, and a
    hand-back entry`
  - `adds the bug label when a ready verdict carries bug: true` and the same for a needs-info verdict
  - `ignores and logs a verdict for an id that wasn't sent to intake`
- **The gate**, in `gate.test.mts`:
  - `readinessReason` holds back an issue without `sandcastle:ready`, or labelled `sandcastle:needs-info` or
    `sandcastle:needs-human`, and lets a ready one through.
  - `gateIssues` holds back each of those, names the reason, and skips the blocker lookup.
- **Beyond the criteria**, added by the backend developer:
  - Only the first verdict on an issue is applied.
  - An issue with no verdict is logged and left unlabelled.
  - The needs-info comment's reason and re-queue note are checked.
  - `intakeRound` skips the run when nothing needs judging.
  - `hasLabel` matches case-insensitively.
- **From review**, in `intake.test.mts` and `github.test.mts`:
  - `adds bug and sandcastle:ready in one edit`
  - `posts nothing when a ready verdict's label edit fails, and judges the issue again next round`
  - `keeps a ready issue's labels and logs it when its comment is rejected, and still applies the next verdict`
  - `adds bug before handing a needs-info verdict back, so a failed bug edit leaves the issue unjudged`
  - `leaves a needs-info verdict with questions … unjudged, and logs it`, for missing, empty and blank questions
  - `skips a verdict on an issue another run has judged since this round read it`
  - `adds several labels to an issue in one edit`
  - `doesn't send an issue another run is building`, `doesn't send an issue whose PR is open, and still sends the
    others`, and `intakeRound` `doesn't judge an issue whose PR is open`
  - `the labels intake adds are all created at startup by ensureLabels`
  - `tells an author without triage access to ask a maintainer to re-queue the issue`
  - the needs-info comment's questions: `drops a blank question`, `keeps a question with a blank line in it to one
    numbered line`, and `doesn't number a question twice when intake numbered it`
  - in `main.test.mts`, `passes intake the open pull requests`
  - `leaves a question that starts with a number alone`
- **Phase 0a and the live intake run**, in `intake.test.mts`:
  - `intakePhase`: `logs an intake run that throws, and carries on`, `logs a queue that can't be read, and carries on
    without running intake`, `rethrows an UncountedStopError`, and `passes intake the issues and open PRs it loaded`.
  - `intakeRunner`, with a stubbed `runRole`: it runs the `intake` role on `intake-prompt.md` with the <code>&#60;intake&#62;</code> tag and
    returns the verdicts. The schema it gives Sandcastle accepts the prompt's example verdicts, and rejects an unknown
    verdict, a missing `bug`, a numeric id and a missing `verdicts` list.

  I checked that each of these goes red with its fix removed.
- **Wiring**, in the new `main.test.mts`: `runs intake before the blocker gate`, checked in `main.mts`'s source.

Sandcastle's own parsing of the <code>&#60;intake&#62;</code> block, such as a missing tag or invalid JSON, isn't exported, so it's
Sandcastle's to test, not this PR's. The tests check what this PR gives it: the role, the prompt, the tag and the
schema.

Sandcastle's gate ran `scripts/gate.sh`, including `pnpm run check:sandcastle`, at both checkpoints, and the pre-push
