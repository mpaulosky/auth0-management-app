# feat(sandcastle): Mark an issue while Sandcastle builds it

- **Release tag:** `v0.0.104`
- **Source PR:** [#219](https://github.com/mpaulosky/Blazor-Server/pull/219)

## PR description

### Why

While Sandcastle built an issue, GitHub showed no sign of it until the PR opened. On 2026-10-07 a manual
`/implement-spec #71` started while Sandcastle was already building #71. Only the run log showed it, and without that two
agents would have edited the same files and raced to publish. A second Sandcastle run could make the same mistake.
This PR marks an issue while it's being built, so people, other agents and other runs leave it alone (#150).

### What changed

- **The `sandcastle:building` label.** It's added to the Labels table in `docs/plans/sandcastle-workflow.md` and to
  `SANDCASTLE_LABELS` in `config.mts`, so `ensureLabels` creates it at startup with the other `sandcastle:*` labels.
- **`buildIssue` marks the issue for the whole build.** It adds the label before creating the issue's sandbox, then
  builds in `buildMarkedIssue`, and removes the label after the sandbox closes. The removal is in a `finally`, so a
  pass, a failure, a red checkpoint, a failed publish or a thrown error all clear it.
  - **Two runs can't both build the issue.** Each round's gate reads labels from a snapshot, so a second run that
    started meanwhile could pick the same issue. Just before adding the label, `claimBuildingLabel` reads the issue's
    labels again. If another run has already added it, this run leaves the issue alone without creating a sandbox or
    counting an attempt, and only the run that added the label removes it. Worktree paths are named after the branch
    alone, so this also keeps the second run out of the first one's worktree. Two runs whose checks land within one GitHub round trip can still
    both add it.
  - **If the label can't be added, the build stops.** Building an unmarked issue is how two runs end up on one issue.
    The error reaches `main.mts`'s `Promise.allSettled`, so only this issue is skipped for the round, and no attempt is
    counted. An add can fail after GitHub has applied the label, as with a timeout, so a failed add is undone at once.
    If that fails too, the run tries again at the start of its next round, and when it exits.
  - **If the label can't be removed, the run carries on.** That's logged, but doesn't replace the build's own result.
    The issue stays on the run's list, so the run retries the removal at the start of each later round, when none of its
    builds is going, and when it exits.
  - **A run never removes another run's label.** The run records when it claimed each label. It never removes one
    claimed more than 6 hours ago, because by then another run may have cleared it as stale and claimed the issue.
- **Stopping a run removes its labels.** `installBuildingLabelRelease` (`lib/building.mts`), called from `main.mts`,
  removes every label the run still holds from a `process.on("exit")` listener, so Ctrl-C, SIGTERM and a crash don't
  leave an issue blocked for 6 hours. It also handles SIGINT and SIGTERM itself with `process.exit`, because the label
  goes on before Sandcastle installs its own signal handler. Sandcastle's handler then never runs, but the `exit`
  listener it installs with it runs the same container teardown. Only a killed process (SIGKILL) gets past this.
- **Startup clears a label a killed run left behind.** The new `lib/building.mts` (`clearStaleBuildingLabels`) runs in
  `main.mts` after `ensureLabels`. It removes the label from any open issue whose most recent `labeled` event for it is
  more than 6 hours old (`BUILDING_LABEL_MAX_AGE_MS`). A newer label belongs to a live run and stays. A timeline that
  can't be read fails the run before any work, rather than guess whether another run is still building. To free an
  issue sooner, remove the label by hand.
- **The 6 hours is checked against the timeouts.** `BUILD_ROLES` in `config.mts` lists the roles `buildIssue` runs,
  with #72's architect, UI developer and scribe counted ahead of time. A test adds up their timeouts, plus every
  gate-fixer attempt at both checkpoints and an hour to spare, and checks the total stays under 6 hours: 245 minutes plus
  an hour today. Another test runs `buildIssue`'s longest path and checks it runs no role outside `BUILD_ROLES`, so a
  role added to `buildIssue` without updating the budget fails the build.
- **New `github.mts` helpers.** `addIssueLabel`, `removeIssueLabel`, `issueLabels`, `issuesWithLabel` and
  `labelTimeline`.
  `labelTimeline` and `jsonLines` were pulled out of `markerComments`, which now uses them. `timestamp` is exported for
  `building.mts`.
- **Where people are told.** The issue asked for `docs/PROCESS.md` to explain the label. `docs/PROCESS.md` is Owned by
  the repo-ci-baseline Template and is overwritten on every Apply, so the note went into `CLAUDE.md`
  (`Don't start work on an issue labelled sandcastle:building`) and the contributing steps in `docs/CONTRIBUTING.md`
  instead. To have it in `docs/PROCESS.md`, the change belongs in the Baseline.
- **Docs and log text.** The phase comments in `main.mts`, the Phase 3 gate text in the plan, and the "every issue is
  waiting" exit message now mention the label.

No mount, sandbox provider or host git call changes. The Ctrl-C path relies on how Node and Sandcastle 0.12 handle
signals. I checked Sandcastle's by reading its source (`registerShutdown`), and Node's with a small script: a SIGINT
handler that calls `process.exit` still runs the `exit` listeners, including a synchronous child process, and skips
later SIGINT listeners. I didn't stop a real run.

### Verification

New tests, by acceptance criterion:

- **The label is on for the build and off afterwards, however it ends**, in `build.test.mts` (`describe("buildIssue
  marking the issue as building")`):
  - `marks the issue as building before the first role runs`
  - `marks the issue before creating its sandbox, and unmarks it after the sandbox closes`
  - `unmarks the issue as building when the tester fails` and the same `when the backend fails`
  - `unmarks the issue as building even when the tester throws an uncounted stop error` and the same for the backend
  - `unmarks the issue as building when a checkpoint stays red past the gate-fixer's attempts`
  - `unmarks the issue as building when publishing fails`
  - `still returns the PR and closes the sandbox when removing the label fails`
  - `marks the issue as building exactly once and unmarks it exactly once per build`
  - `runs only BUILD_ROLES, each once, and the gate-fixer at most its attempts per checkpoint, on the longest build`
  - `leaves the issue alone when another run marked it first, without a sandbox or counting an attempt`
  - `stops the build before creating a sandbox, without counting an attempt, when the label can't be added`
- **Claiming and releasing the label**, in `building.test.mts`:
  - `claimBuildingLabel` adds the label to an unmarked issue and remembers it. It leaves an issue another run already
    marked (`Sandcastle:Building`, in another case) without adding the label. When the add fails, it undoes it and
    forgets the issue, or keeps remembering it if the undo fails too.
  - `releaseBuildingLabel` removes the label and forgets the issue, but keeps remembering it when the removal fails.
  - `releaseAllBuildingLabels` removes every label the run holds, carries on past one that fails and reports it, removes
    it on a later call, and forgets without removing a label claimed more than 6 hours ago.
- **The gate holds a labelled issue back**, in `gate.test.mts`: `holds back an issue carrying sandcastle:building, names
  it in the reason, and skips its blocker lookup`.
- **A label over 6 hours old is cleared at startup and a newer one is kept**, in `building.test.mts`, with stubbed
  timeline events:
  - `labelIsStale`: stale past the max age, not stale within it, uses the most recent `labeled` event, and not stale
    with no `labeled` event.
  - `clearStaleBuildingLabels`: removes a stale label, keeps a recent one, clears only the stale ones among several
    issues, reads only the timelines of issues carrying the label, and lets a timeline that can't be read throw without
    removing anything.
- **Releasing the labels when the run stops**, in `building.test.mts`:
  - `installBuildingLabelRelease`, with a process stub: SIGINT exits with 130 and SIGTERM with 143, so the exit listener
    runs, and the exit listener releases and logs each label.
  - `main.mts`'s wiring, checked in its source because the module runs at import: the release is installed and stale
    labels are cleared after `ensureLabels` and before the first round, and the labels the run still holds are released
    at the start of each round, before the gate.
- **The `gh` calls**, in `github.test.mts`: adding, removing, reading and listing issue labels, and reading a paginated
  timeline.
- **The 6-hour limit**, in `config.test.mts`: `outlasts the longest build the role timeouts allow, with an hour for gates,
  sandboxes and publishing`.

The `main.mts` checks read its source for the order of the calls rather than running it, so they'd miss a call that
was present but never reached.

I checked that the tests go red when the code they guard is broken: removing the label without this run having added
it, dropping the install call from `main.mts`, moving the per-round release after the gate, leaving `reviewer` out of
`BUILD_ROLES`, and dropping the SIGTERM handler. `pnpm run check:sandcastle` passes (314 tests), with #218 merged in.

Sandcastle's gate ran `scripts/gate.sh`, including `pnpm run check:sandcastle`, at both checkpoints, and the pre-push
hook ran it again on the review fixes.

Closes #150
