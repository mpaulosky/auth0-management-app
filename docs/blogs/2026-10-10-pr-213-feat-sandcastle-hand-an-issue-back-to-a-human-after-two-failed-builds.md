# feat(sandcastle): Hand an issue back to a human after two failed builds

- **Release tag:** `v0.0.101`
- **Source PR:** [#213](https://github.com/mpaulosky/Blazor-Server/pull/213)

## PR description

### Why

An issue whose build fails every round was rebuilt forever, spending a full tester, backend, gate and review cycle each
time with no sign to a person that it was stuck. This caps it at two failed attempts and then hands the issue back with
`sandcastle:needs-human`. The count is kept in marker comments on the issue, so it survives restarts. This also adds the
shared hand-back helpers that intake (#74) and the PR follow-up passes (#77, #78) will use.

### What changed

- **Failed build attempts** (`lib/build.mts`, `lib/handback.mts`). A failed attempt is anything that stops the issue's
  pipeline: the gate still red after the gate-fixer's attempts at either checkpoint, or a tester or backend run that
  fails or times out. Each posts an issue comment with <code>&#60;&#33;&#45;&#45; sandcastle&#58;build&#45;failed &#45;&#45;&#62;</code>, the attempt number, and the
  tail of the gate output or the role's error. The second attempt hands the issue back instead.
  - A reviewer failure still publishes and doesn't count, and neither does a gate-fixer run that fails with attempts left.
- **The count** (`markerCommentsSince` and `markerComments` in `lib/github.mts`) counts only marker comments posted since
  `sandcastle:needs-human` was last removed, read from the issue's timeline. So when a person removes the label, the
  issue is back in the queue with a fresh count. Only comments from the login `gh` is signed in as count (`hostLogin`),
  so a stranger can't paste the marker in to hand an issue back early. That login is used rather than the repository
  owner because, for a copy of the template that an organization owns, the owner never posts. The check runs in
  `markerCommentsSince`, not in the `gh` query, so it's tested.
- **Hand-back** (`lib/handback.mts`): posts one comment, then adds `sandcastle:needs-info` or `sandcastle:needs-human`,
  then records the hand-back for the end-of-run summary (`HandBackReport` in `lib/report.mts`). Commenting first means a
  rejected comment leaves the issue in the queue. The give-up summary quotes every failure, each trimmed to an equal share
  of GitHub's 65,536-character comment limit, keeping its heading and the end of its output. The last attempt is quoted as
  its own heading and detail, so the summary never says the issue stays in the queue. An issue-level
  `needs-human` also removes `sandcastle:ready`. `main.mts` lists the run's hand-backs at the end.
- **Usage and time stops don't count.** `UncountedStopError` (in the leaf module `lib/errors.mts`, so the role runner
  can throw it without an import cycle) marks a stop caused by the usage limit or the run's time
  budget. Every role, the reviewer included, and the gate-fixer rethrow it, so the round ends without spending an
  attempt or publishing unreviewed work. Nothing throws it yet: detecting those stops is #147's job, and #147 now
  says to throw this error. Until then, a usage-limit stop still counts as a failed attempt. Every run until #147 is
  started by hand, and removing `sandcastle:needs-human` undoes a wrong hand-back and resets the count.
- **Labels** (`ensureLabels`, `SANDCASTLE_LABELS` in `lib/config.mts`): at startup, any missing `sandcastle:ready`,
  `sandcastle:needs-info` or `sandcastle:needs-human` label is created with the colour and description from the spec.
  A label another run created at the same moment counts as created, so concurrent starts don't crash. The host's login
  is read at startup too, so a token that can't read it fails before any role runs.
- `BUILD_FAILURE_CAP` (2) and `BUILD_FAILED_MARKER` live in `lib/config.mts`. `docs/plans/sandcastle-workflow.md` and the
  `main.mts` header describe the new behaviour.

### Verification

New tests in `lib/build.test.mts`, `lib/github.test.mts`, `lib/handback.test.mts` and `lib/checkpoint.test.mts`, with
stubbed `gh` output and timeline data, cover each acceptance criterion:

- The first failed build posts an attempt-1 comment and leaves the issue in the queue.
- The second adds `sandcastle:needs-human`, removes `sandcastle:ready` and posts the summary.
- Comments posted before `needs-human` was last removed don't count, and the label's most recent removal is the one
  used.
- A marker comment posted by anyone but the host's own login doesn't count, and `hostLogin` reads that login from `gh`.
- The give-up summary, and a single failed attempt's comment, stay under GitHub's comment limit with long output,
  keeping the end of the output and balanced code fences.
- A rejected hand-back comment leaves the labels alone and records nothing.
- `markerComments`, fed recorded `gh` output (paginated comments, label events, a `created_at` with a trailing newline),
  returns only the host's marker comments since the label's removal.
- A usage-limit or time-budget stop posts no failure comment, from a developer role, the reviewer or the gate-fixer.
- Missing labels are created, and existing ones (matched case-insensitively) aren't. An "already exists" from a
  concurrent create isn't an error; any other create failure is.
- The login read at startup is reused, with no further `gh api user` call.

Sandcastle's sandbox ran `scripts/gate.sh`, including `pnpm run check:sandcastle`, after the build and again after its
review, and it passed both times.

### Out of scope

- **Throwing `UncountedStopError`.** This PR adds the error and makes every role and the gate-fixer rethrow it. Detecting
  a usage-limit or time-budget stop and throwing it is #147's scope (its issue says so). Until then, those stops count as
  failed attempts. Runs are started by hand until #147 lands, because unattended runs (#82) wait on it.
- **Failing the run on a hand-back.** This PR records the hand-backs and logs them at the end. Failing the job is the
  trigger workflow's final step (#82), reading the list #81 writes. Exiting non-zero here would make a local run look
  like a crash.
