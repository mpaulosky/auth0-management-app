# ci(sandcastle): Add switched-off triggers for follow-up runs

- **Release tag:** `v0.0.17`
- **Source PR:** [#60](https://github.com/mpaulosky/auth0-management-app/pull/60)

## PR description

### Why

#53 (follow-up passes wait behind a running build) and #58 (follow up on hand-opened PRs labelled for it) each need a change to `.github/workflows/sandcastle.yml`. Sandcastle's token has no Workflows permission, so its own PRs for those issues can't include it. This PR lands the workflow side ahead of the host code, switched off, so neither issue waits on a second hand-made PR later.

### What changed

Both changes sit behind repository variables. While a variable is unset, the workflow behaves exactly as before.

- **`SANDCASTLE_FOLLOW_UP_JOB=true` (#53):** a run started by `pull_request_review`, `workflow_run` or `pull_request_target` (the follow-up label, or a hand-back removal on a PR) takes the concurrency group `sandcastle-follow-up` instead of `sandcastle`, and the Run Sandcastle step sets `SANDCASTLE_MODE=follow-up`. Every other run is in `sandcastle` with the mode empty. A small first job, **Choose the run mode**, carries the event filter and decides the mode once. The concurrency group and `SANDCASTLE_MODE` both read its output, so they agree even if the variable changes while a run waits in its pending slot.
- **`SANDCASTLE_FOLLOW_UP_LABEL=true` (#58):** the workflow also triggers on `pull_request_target: labeled`. The job runs when the owner adds exactly `sandcastle:follow-up` to a same-repo PR. The review and `workflow_run` conditions also accept `chore/` heads.
- **PR label events come from `pull_request_target`** (`labeled` and the existing `unlabeled`): GitHub starts no `pull_request` run on a PR with merge conflicts. The job checks out `main` either way. A PR's label event counts only for a same-repo PR into `main`: `pull_request_target` gives a fork's PR the secrets, and runs the workflow file from the PR's base branch.
- **`docs/plans/sandcastle-workflow.md`:** documents both variables, under "Triggers" and next to "Overlap". It also states two host requirements. First, keep a full run and a follow-up run off the same PR before `SANDCASTLE_FOLLOW_UP_JOB` is set. Second, ignore the job's own `Sandcastle` check on a PR's head, which runs while the run does and turns red for a hand-back on any issue.

I added a "Workflow contract" section to #53 and #58, so the host side Sandcastle builds matches these names. In follow-up mode the host runs only the sweep and passes, once, and exits. It also needs a guard so a follow-up run and a full run never push to the same branch, and it ignores the job's own `Sandcastle` check (already a latent problem for `pull_request_review` runs).

### Rollout

1. Merge this PR. Nothing changes while the variables are unset.
2. When #53's host PR merges, set `SANDCASTLE_FOLLOW_UP_JOB=true` (Settings → Secrets and variables → Actions → Variables).
3. When #58's host PR merges, set `SANDCASTLE_FOLLOW_UP_LABEL=true`.

Don't set `SANDCASTLE_FOLLOW_UP_JOB` before #53's host side lands. Today's host ignores `SANDCASTLE_MODE`, so a run in the new group would do a full intake and build alongside the main run.

`pull_request_target: labeled` now starts the workflow for every label added to any PR. The job's `if:` skips all of those but the owner's `sandcastle:follow-up`, as it already does for `unlabeled`.
