# feat(aspire): Serve WebApp over HTTPS from the AppHost's https profile

- **Release tag:** `v0.0.151`
- **Source PR:** [#343](https://github.com/mpaulosky/Blazor-Server/pull/343)

## PR description

### Why

The AppHost always started the UI on its `http` launch profile, so that it could run where there's no developer
certificate (CI, the Sandcastle sandbox). Local runs through Aspire were HTTP-only as a result, even with a trusted
certificate, and sign-in over HTTP works only on `localhost`.

### What changed

- `src/AppHost/AppHost.cs` no longer names a launch profile for `WebApp`. Aspire then starts the UI with its launch
  profile of the same name as the AppHost's: `aspire run` and the AppHost's `https` profile serve WebApp at
  `https://localhost:7161`, and its `http` profile keeps WebApp on `http://localhost:5112`.
- `AppHostTests` and the E2E `WebAppFixture` pass `--DOTNET_LAUNCH_PROFILE=http`, because the testing builder otherwise
  applies the AppHost's first profile, `https`, and the UI would need a certificate. `--launch-profile=http` doesn't
  work here: the testing builder ignores it.
- New `LaunchProfileTests` check that each AppHost profile picks the UI profile of the same name.
- The README covers the `https` profile and trusting the certificate, including the `SSL_CERT_DIR` step .NET needs on
  Linux. `CLAUDE.md` describes the new launch-profile behaviour.

### Verification

- `scripts/gate.sh` passes, including `AppHost.Tests.Integration` and `UI.Tests.E2E`, which still run over HTTP.
- `LaunchProfileTests` failed for `https` before the change and pass after it.
- Started the AppHost with no profile, `--launch-profile https` and `--launch-profile http`. With `https`, WebApp
  answered `/health` on `https://localhost:7161` with a trusted certificate, and `:5112` redirected to it. With `http`,
  only `:5112` answered.
- Signed in through Auth0 by hand over HTTPS: the callback is `https://localhost:7161/callback`.
