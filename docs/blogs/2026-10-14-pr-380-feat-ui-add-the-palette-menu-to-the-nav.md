# feat(ui): Add the Palette menu to the nav

- **Release tag:** `v0.0.162`
- **Source PR:** [#380](https://github.com/mpaulosky/Blazor-Server/pull/380)

## PR description

Closes #366

### Why

The Palettes slice already stored a visitor's chosen accent hue in a `palette` cookie and rendered it as `data-palette` on <code>&#60;html&#62;</code>.
Nothing in the UI posted to it, though, so visitors couldn't change the accent color.
This branch adds the Palette menu to the nav, on desktop and in the mobile menu, so any Visitor or User can pick one of the 17 hues.
It works without JavaScript.

### What changed

- `src/UI/Components/Features/Palettes/PaletteMenu.razor` is a new, statically rendered component.
  It renders one <code>&#60;form method&#61;&#34;post&#34; data&#45;enhance&#62;</code> that posts to the base-relative `palette` action, with an antiforgery token and a hidden `returnUrl`.
  The form holds 17 submit buttons named `palette`, in the `Palette` enum's order (Red to Rose).
  Each button's value is the hue's lowercase name, and its accessible name is the hue's name.
  Each one shows an `aria-hidden` swatch in the hue's own <code>bg&#45;&#60;hue&#62;&#45;500</code>.
  The current hue's button (Blue when there's no cookie) has `aria-pressed="true"` and a ringed swatch.
- On desktop, the form sits in a <code>&#60;details&#62;</code> dropdown.
  Its <code>&#60;summary&#62;</code> is labelled <code>Palette&#58; &#60;Hue&#62;</code> and shows the current hue's swatch.
  With `Mobile="true"` there's no dropdown: the form sits in a <code>&#60;section&#62;</code> under an <code>&#60;h2&#62;</code> that reads "Palette".
  Every new surface has `dark:` variants, and every accent color uses `accent-*`, except the swatches' own hue classes.
- `src/UI/Components/Layout/NavMenu.razor` renders <code>&#60;PaletteMenu&#47;&#62;</code> after the Theme control in the desktop <code>&#60;nav&#62;</code>.
  It renders <code>&#60;PaletteMenu Mobile&#61;&#34;true&#34;&#47;&#62;</code> after the Theme control in the mobile <code>&#60;details&#62;</code> menu.
- `README.md` now describes the Palette as built, and the Roadmap section, which had only the Palette left in it, is removed.
  `CLAUDE.md`'s opening paragraph names the Palette menu in the `Palettes` slice.

There was no architect's design note for this issue.
The component follows the class lists and markup in `docs/plans/theme-and-palette.md`, and it follows the pattern `ThemeControl` already uses.

### Verification

- `tests/UI.Tests.Unit/Components/Features/Palettes/PaletteMenuTests.cs` (bUnit, new) checks:
  - the single form, with its method, `data-enhance`, base-relative action, antiforgery token and `returnUrl`
  - the 17 buttons' names, values, order, accessible names and swatch classes
  - which button has `aria-pressed`, for no cookie, `rose` and an unknown value
  - the desktop summary's label and swatch, and the mobile heading with no <code>&#60;details&#62;</code>
- `tests/UI.Tests.Unit/Components/Layout/NavMenuTests.cs` adds tests that the Palette menu follows the Theme control in both the desktop nav and the mobile menu.
  The tests that look for the mobile menu now use the `header > div > details` selector.
  Without it they would find the desktop Palette menu's own nested <code>&#60;details&#62;</code> instead.
- `tests/UI.Tests.E2E/PaletteTests.cs` (Playwright, through the AppHost) opens the desktop Palette menu and chooses Rose.
  It checks that <code>&#60;html&#62;</code> has `data-palette="rose"` and that the attribute is still there after a reload.
- `scripts/gate.sh` passed on the final branch: lint, the Release build, and every test project.
  The counts were 379 UI unit, 88 UI integration, 30 Domain, 5 AppHost and 26 architecture tests.
  The E2E project had 10 passed and 1 skipped: the existing Auth0 login test, which needs a real Auth0 tenant.
