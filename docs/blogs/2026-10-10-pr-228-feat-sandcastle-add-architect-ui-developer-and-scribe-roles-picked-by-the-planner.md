# feat(sandcastle): Add architect, UI developer and scribe roles picked by the planner

- **Release tag:** `v0.0.107`
- **Source PR:** [#228](https://github.com/mpaulosky/Blazor-Server/pull/228)

## PR description

Closes #72

### Why

Every issue ran the same tester → backend → reviewer pipeline. An issue that needs a design up front, Blazor UI work
or documentation got none of that, and an issue that needs none of it shouldn't pay for extra runs. #72 has the
planner pick three optional roles per issue (architect, UI developer and scribe), and the host runs each one in its
place in the build order. Spec: "Phase 4: Plan" and "Phase 6: Build" in `docs/plans/sandcastle-workflow.md`.

### What changed

- **Planner picks roles.** Each pick in the plan has a `roles` list (`plan-prompt.md` says when to pick each role).
  `resolveRoles` (`lib/plan.mts`) keeps the roles it recognises, without repeats and in build order. A missing or
  invalid field runs every optional role and doesn't fail the plan, so the schema leaves the field `unknown`. <code>&#91;&#93;</code> is
  a deliberate "none". `OPTIONAL_ROLES` is in `lib/config.mts`.
- **Roles survive the critique.** In `main.mts`, the critique only filters picks, so each kept pick gets its roles
  back by issue number. The "Planning complete" log names each issue's optional roles.
- **Build order** (`buildIssue`, `lib/build.mts`): [architect] → tester → backend → [ui] → checkpoint 1 → [scribe] →
  reviewer → checkpoint 2 → publish. Issues take a new `RoledIssue` type.
- **Architect** (`roles/architect.md`):
  - It writes <code>&#46;sandcastle&#47;work&#47;&#123;n&#125;&#47;design&#46;md</code> (newly gitignored) and no production code. It adds an ADR only for a
    decision that is hard to reverse, surprising, and a real trade-off.
  - The host reads the note inside the sandbox, not from the host, because an agent wrote it and it could be a
    symlink. `designComment` posts the note on the issue under <code>&#60;&#33;&#45;&#45; sandcastle&#58;design &#45;&#45;&#62;</code> (`DESIGN_MARKER`):
    - The note goes through `publicErrorText` first and is cut at 60,000 characters.
    - Every <code>&#60;&#33;&#45;&#45;</code> in it is broken with a zero-width space, so a quoted host marker can't pass for a host comment.
      `markerComments` matches by substring, so a quoted <code>&#60;&#33;&#45;&#45; sandcastle&#58;build&#45;failed &#45;&#45;&#62;</code> would otherwise count as
      a failed attempt.
    - The note sits in a code fence longer than any backtick run in it, so it can't mention anyone or cross-reference
      another issue.
    - `designNoteIn` reads the note back exactly as written.
  - On a re-run, the architect's prompt gets its latest earlier note, read after the last `sandcastle:needs-human`
    hand-back, so a rewritten issue starts fresh.
  - A missing note, or a comment that fails to post, is logged. Neither counts as a failed build.
- **UI developer** (`roles/ui.md`) is split from the backend prompt and handles Blazor components and pages.
  `backendPromptArgs` tells the backend developer whether the UI developer runs after it. If it does, the backend
  leaves those files to it. If it doesn't, the backend's run is the last developer run.
- **Scribe** (`roles/scribe.md`):
  - It owns `CONTEXT.md` terms, `README.md` prose and hand-written guides.
  - It stays off the release-generated files, and it creates no ADRs.
  - It commits nothing when there's nothing to document.
- **Failures:**
  - An architect or UI developer failure stops the issue the same way a tester or backend failure does: it's a failed
    build attempt and nothing is published.
  - A scribe that fails or runs out of iterations still publishes. `publish` takes `docsFailed`, and the PR body then
    says the documentation step failed.
  - A usage limit or time budget still ends the run.
- **Prompts:** the tester, backend and reviewer prompts point at the design note. The reviewer checks that any
  departure from the note is explained in a commit body.

### Verification

- `build.test.mts`:
  - Only the roles the plan picked run: scribe only, every role, or none.
  - Every optional role runs in its place in the build order.
  - An architect or UI failure stops the build and counts as a failed attempt, and a usage stop is rethrown.
  - The design note is posted with its marker, and fed back to the architect on a re-run.
  - A note that looks like it holds a secret is withheld. A missing note posts nothing, and a comment that fails to
    post is only logged; the build still publishes in both cases.
  - `designComment` and `designNoteIn`: a note quoting `BUILD_FAILED_MARKER` and `DESIGN_MARKER` carries only the
    leading design marker; the fence is longer than any backtick run; an over-long note is cut with a notice; and the
    note reads back exactly as written. I checked each test by removing the code it covers and confirming it turns
    red.
  - A scribe that fails or runs out of iterations still publishes with the note. A scribe that succeeds publishes with
    no note, and a usage stop from the scribe is rethrown.
  - The `BUILD_ROLES` budget test runs every role once on the longest build.
- `plan.test.mts` covers `resolveRoles`: a missing field, a field that isn't an array, an unknown role, a role named
  twice, and <code>&#91;&#93;</code>.
- `prompts.test.mts` covers `architectPromptArgs` and `backendPromptArgs`. `role-prompts.test.mts` covers each prompt's
  wiring.
- `main.test.mts` checks with `git check-ignore` that `.sandcastle/work/` is ignored.
- I merged `main` (intake, #222/#225) into the branch, keeping both sides of the `main.mts` imports and of the
  `prompts.test.mts` and `main.test.mts` tests. `pnpm run check:sandcastle` passes (431 tests), and so does
  `scripts/gate.sh` on push.
