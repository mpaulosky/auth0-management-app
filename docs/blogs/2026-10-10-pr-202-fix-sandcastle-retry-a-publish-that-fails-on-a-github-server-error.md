# fix(sandcastle): Retry a publish that fails on a GitHub server error

- **Release tag:** `v0.0.100`
- **Source PR:** [#202](https://github.com/mpaulosky/Blazor-Server/pull/202)

## PR description

### Why

When `git push` hit a transient GitHub error, a branch that had already been built, gated and reviewed was lost for the
round. On 2026-10-07, #71 passed both gate checkpoints, then publishing it failed with `remote: Internal Server Error`.
The run reported "No pull requests opened this round. Stopping." as if there had been nothing to build, and it posted
nothing to the issue. The work only shipped because someone pushed it by hand after GitHub recovered (#148).

### What changed

- `publish` in `.sandcastle/lib/build.mts` retries `git push` and `gh pr create` when either fails with a GitHub server
  error. It tries each step up to `PUBLISH_RETRY_ATTEMPTS` (4, in `lib/config.mts`) times in all, waiting 5 s, then
  10 s, then 20 s.
  - `isGitHubServerError` decides what counts as a server error. It matches what git and gh print for one
    (`Internal Server Error`, `returned error: 502`, `HTTP 503`, `Bad Gateway`, `Service Unavailable`,
    `Gateway Timeout`, and GraphQL's `Something went wrong while executing your query`, which GitHub sends with HTTP 200
    on a timeout), not a bare `5xx`, since a branch name can hold one (`fix/500-...`). It reads only the command's
    output after `failed:`, not the command line before it, so a branch name or an issue title there can't trigger a retry.
  - Nothing else is retried. A push that doesn't fast-forward still fails at once, because a person needs to look at
    it either way.
  - A retried `gh pr create` doesn't open a second PR. `openPullRequest` looks for an open PR from the branch first.
- When publishing still fails after the retries, the issue comment says the branch passed the gate and keeps its
  commits. It tells the reader to check first whether a pull request from it is already open (GitHub can create one and
  still answer with an error). Then, once GitHub recovers: if origin's branch isn't at the commit the gate passed (the
  comment names it), push it from its worktree; if it is, the push worked and only the pull request failed, so open one
  with `Closes #N`.
- `buildIssue` returns `publishFailed`. The round summary has moved from `main.mts` to the new `lib/round.mts`
  (`roundSummary`). It lists stranded branches separately, and when every gated branch failed to publish, the run stops
  with "Publishing failed for every gated branch this round" instead of "No pull requests opened this round".
- `docs/plans/sandcastle-workflow.md` describes the retry.

### Verification

- New tests in `lib/build.test.mts` and `lib/round.test.mts`, using a stubbed push, PR creation and wait:
  - A push, or a `gh pr create`, that fails with a server error and then succeeds still opens the PR.
  - A push rejected for any other reason isn't retried.
  - A step that still fails with a server error after every attempt is rethrown, and the issue gets a comment and no PR.
  - A client error, or a branch name containing `500`, isn't taken for a server error.
  - A server-error phrase in the quoted command line, such as an issue title, isn't taken for a server error.
  - The round summary names a publish failure, and doesn't report it as a round that built nothing.
- Sandcastle's sandbox ran `scripts/gate.sh`, including `pnpm run check:sandcastle`, after the build and again after
  its review, and it passed both times.

Closes #149
