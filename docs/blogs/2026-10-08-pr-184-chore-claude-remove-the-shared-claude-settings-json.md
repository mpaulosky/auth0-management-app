# chore(claude): Remove the shared .claude/settings.json

- **Release tag:** `v0.0.88`
- **Source PR:** [#184](https://github.com/mpaulosky/Blazor-Server/pull/184)

## PR description

### Why

The repo-ci-baseline Template stopped shipping Claude Code settings: permissions are set per user, so the Baseline says not to add `.claude/settings.json` back. It was deleted in the primary checkout by hand but the deletion was never committed (mpaulosky/dotfiles#127).

### What changed

- Removes `.claude/settings.json`. Its only content was deny rules for reading and editing `.env` files. Those rules now live in each user's `~/.claude/settings.json` (the maintainer's already has them, plus `Edit(./.sandcastle/.env)`).
- `docs/SECURITY.md` says so instead of promising repo-level settings. It gives the exact `permissions.deny` block for contributors to add to their own `~/.claude/settings.json`, and says what they leave open: they bind Claude Code's file tools under the session's project, not shell commands; their `.env.*` patterns also hide committed `.env.example` files; and they cover sessions on the contributor's own machine only (a Sandcastle sandbox has its own settings, and gets `.sandcastle/.env`'s values as environment variables anyway). Existing clones lose the repo-level rules on their next pull.
- The layout in `README.md` and `docs/README.md` lists `.claude/` as instructions, rules and skills, without settings.

**Dependency:** the repo-ci-baseline Template already dropped `.claude/settings.json` (its SKILL.md: "not part of the Template … don't add the file back"), so a re-Apply won't recreate it.

### Verification

- `git ls-tree origin/main .claude/` on Articles, TicketManager, IssueTracker and IssueManager: none of them track a `settings.json`, so this brings Blazor-Server in line.
- The pre-push gate (`scripts/gate.sh`) passed on each push.
