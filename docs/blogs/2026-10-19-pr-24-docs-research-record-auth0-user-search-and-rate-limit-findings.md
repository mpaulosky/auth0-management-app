# docs(research): Record Auth0 user search and rate limit findings

- **Release tag:** `v0.0.8`
- **Source PR:** [#24](https://github.com/mpaulosky/auth0-management-app/pull/24)

## PR description

### Why

The map [Manage Users and Roles](https://github.com/mpaulosky/auth0-management-app/issues/11) asked what Auth0's User search, paging and rate limits mean for a searchable, paged User list ([#13](https://github.com/mpaulosky/auth0-management-app/issues/13)). This PR records the answer in the repo, so the User list's design ([#16](https://github.com/mpaulosky/auth0-management-app/issues/16)) can build on it.

### What changed

- `docs/research/auth0-user-search-and-rate-limits.md` records the findings from Auth0's docs and the Management API v2 reference:
  - Search `GET /api/v2/users` with a Lucene `q` and `search_engine=v3`. Prefix search works, and the normalized profile fields match case-insensitively.
  - The endpoint reference allows 100 Users a page, but the API overview says 50 on Public Cloud, so use 50 or less. `include_totals=true` adds the total.
  - The Admin's search text has to be lowercased and escaped before it goes into `q`, and kept as one prefix term because v3 fields aren't tokenized. The note recommends how to build the query, to be checked against a live Tenant.
  - Search reaches only the first 1000 matches. Past that, the query has to be narrower.
  - Search is eventually consistent: a lookup by ID shows a change right away, but search results can lag.
  - Rate limits apply per Tenant and depend on the plan's tier, from 2 requests a second on the Free plan upward. A 429 carries `X-RateLimit-*` headers.
  - A page's first load can exceed the burst: the User detail page makes three calls, and listing who holds each Role costs one call per page of each Role's members. Auth0 answers a call over the limit with a 429 rather than queueing it. The note recommends a client-side token bucket per Auth0 limit and a short cache, and leaves 429 retries to the SDK, as ADR 0009 does.
