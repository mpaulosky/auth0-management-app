# feat(sandcastle): Replace the implementer with a tester and a backend developer

- **Release tag:** `v0.0.75`
- **Source PR:** [#148](https://github.com/mpaulosky/Blazor-Server/pull/148)

## PR description

### Why

Until now, one Sandcastle implementer wrote both the tests and the code for an issue. That let the same run write tests that already matched what it built. This change splits the work in two. A tester turns each acceptance criterion into failing tests and commits them red, and a backend developer then makes them pass. The reviewer gains two checks: that the tests cover every acceptance criterion, and that nobody weakened them. This is the "Phase 6: Build" step of `docs/plans/sandcastle-workflow.md`.

### What changed

- **Role prompts.** `.sandcastle/roles/tester.md` writes failing tests for each acceptance criterion, adds stubs that only throw `NotImplementedException`, builds, lints its own files and commits red. It doesn't run the gate. `.sandcastle/roles/backend.md` is split out of `implement-prompt.md`: it makes the tests pass one by one and runs `scripts/gate.sh` as its last step. Both prompts receive the shared rules and list the six `dotnet-*` skills mounted into the sandbox. The comment on `SANDBOX_SKILLS` in `lib/skills.mts` now names both prompts.
- **Removed:** `implement-prompt.md` and the `implementer` entry in `ROLE_AGENTS`.
- **Build order** (`lib/build.mts`): tester → backend → gate checkpoint 1 → reviewer → gate checkpoint 2 → publish. Each role and checkpoint is logged with the issue number when it finishes. A `log` hook on `BuildHost` lets the tests check that order; a real run writes to `console.log`.
- **Developer failure.** If the tester or backend developer throws, times out or runs out of iterations without finishing, the issue stops for the round. Nothing is gated or published, the branch keeps its commits, and the issue gets a comment naming the role and the reason, the same way a red checkpoint does.
- **The tester can finish without a new commit.** It completes once every criterion that can be tested automatically has a committed test. That includes a re-run whose tests already exist, and an issue whose criteria are all manual. It names untestable criteria in its commit body, or in its final message when it commits nothing.
- **`review-prompt.md`** checks that the acceptance tests cover every criterion and that the developers didn't weaken them: no removed or loosened assertions, no skipped, commented-out or deleted tests, and no expected values changed to match the code.

Decisions worth a look:

- **A failed tester or backend run doesn't throw.** `buildIssue` comments on the issue and returns no PR, like a red checkpoint, so `main.mts` doesn't count it as a crashed build. Issue #73 can add its failed-build marker to that comment.
- **The reviewer may add or restore an acceptance test** for a criterion that can be tested automatically, when the test is missing or was weakened. The issue only asked for the checks, but without this a reviewer could only report the problem. It checks criteria that can't be tested automatically against the change directly.
- **`lib/role-prompts.test.mts`** checks the prompt files themselves. The review-prompt tests look for key terms anywhere in the review-process section, ignoring case, so rewording a check doesn't break them but dropping one does.

### Verification

- `pnpm run check:sandcastle`: 126 tests pass. New tests cover the build order, the log order, each tester and backend failure mode with its issue comment, the commits kept after a failure, and the role prompts.
- `scripts/gate.sh` passed at both Sandcastle checkpoints and again in the pre-push hook after merging `main` and after the review fixes.
