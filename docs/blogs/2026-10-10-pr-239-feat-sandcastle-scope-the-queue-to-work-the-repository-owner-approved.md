# feat(sandcastle): Scope the queue to work the repository owner approved

- **Release tag:** `v0.0.112`
- **Source PR:** [#239](https://github.com/mpaulosky/Blazor-Server/pull/239)

## PR description

Closes #146

### Why

Any issue carrying `Sandcastle` reached an agent, whoever added the label, and a local run competed with GitHub Actions for the whole queue. The spec's "Labels" section says only work the repository owner queued and approved may reach an agent. It says a local run must name what it works on, and that Sandcastle's own labels count only when the owner set or cleared them. Split from #80.

"The repository owner" means any login with `admin`, `maintain` or `write` permission, the same check #214 added for comments.

### What changed

**Queue scope (`lib/config.mts`, `main.mts`).**

- `queueScopeFrom(process.env)` runs first, before git, gh or a sandbox is touched.
- In GitHub Actions the queue is always `Sandcastle`. Setting `SANDCASTLE_ISSUE` or `SANDCASTLE_LABEL` there is refused, not ignored.
- Locally, exactly one of these must be set:
  - <code>SANDCASTLE&#95;ISSUE&#61;&#60;n&#62;</code>: only that issue and its PR;
  - <code>SANDCASTLE&#95;LABEL&#61;&#60;label&#62;</code>: for example `Sandcastle:dev`, or `Sandcastle` itself as an explicit opt-in.
- The run prints the usage message and exits with status 2 for any of these:
  - neither variable set, or both;
  - a non-numeric issue;
  - a label over 50 characters;
  - a label with a comma or double quote, which gh's `--label` would split;
  - a label the host manages (`sandcastle:*`, `bug`).
- The scope is logged at startup (`Queue: issues labelled …`).
- `.sandcastle/.env.example`, `main.mts`'s header and `CLAUDE.md` show both forms.

**Owner-approved queue (`lib/queue.mts`, new).**

- `loadQueue()` replaces the direct `listSandcastleIssues()` reads in the gate, intake and the follow-up sweep, so every phase filters the same way.
- It keeps an issue only when both of these hold:
  - the most recent `labeled` event adding the queue label was the owner's;
  - no `renamed` event or body edit (GraphQL `userContentEdits`) by anyone else falls at or after that add. A same-second edit counts as after, and so does an unparseable time.
- Other issues are skipped and logged once per run, with no comment and no write.
- The host's own login always counts as the owner (`ownerCheck`), so its own label changes pass even when GitHub Actions' host acts as a GitHub App whose <code>&#91;bot&#93;</code> login has no collaborator permission. Those changes include intake's `sandcastle:ready`, a split's children and `loadQueue`'s restores.
- Each issue's events and body edits are read once a round, not once per phase. `startQueueRound()` runs at the top of each round. The cache key is the issue's `updatedAt`, labels, title and body, so a change between phases is read again. That covers intake's own writes, and a label someone removed and added back.
- A permission lookup that fails holds the issue back for the round. It never lets an issue through or triggers a write.

**Label origin (`labelOriginFixes`).**

- Issues:
  - `sandcastle:ready` is trusted only when the owner's add is its most recent. A non-owner's add is removed, so intake judges the issue again. When no add event shows at all (GitHub's list may lag intake's own write), the issue is held for the round and nothing is written.
  - A removal of `sandcastle:needs-info` or `sandcastle:needs-human` counts as a re-queue only when the owner made it; otherwise the label is put back.
  - If a label fix fails, the issue is skipped rather than guessed at.
- PRs: the sweep restores a PR-level `sandcastle:needs-human` that someone else removed, and leaves that PR alone for the round.

**Scope-aware intake and umbrellas.**

- A split under a label scope moves that scope's label from the original issue to its children.
- `closeFinishedUmbrellas` considers only the scope's issue in issue scope. It also treats the scope's label, matched case-insensitively, as holding an umbrella open.

**GitHub reads (`lib/github.mts`).**

- `pushAccess`: a three-way answer (yes, no, or lookup failed), cached per login for the run. Revoked write access is seen from the next run.
- `issueEvents`: shape-checked, so an unexpected event throws rather than being read as nobody's.
- `bodyEdits`.
- `addPullRequestLabel`.
- `listSandcastleIssues` now takes a scope.

### Verification

- `pnpm run check:sandcastle` passes, with 71 new tests:
  - `config.test.mts`: every `queueScopeFrom` outcome, including the Actions refusals and each host-managed label.
  - `queue.test.mts`: `approval`'s add, rename and edit timing, including same-second edits, ties, re-adds, deleted accounts and unknown permission; `labelOriginFixes`; and `loadQueue` end to end with stubbed events. The stubbed-event cases cover:
    - a stranger's label;
    - the host's own split labels;
    - a stranger's edit or rename;
    - a stranger's `sandcastle:ready`;
    - a hand-back label a stranger removed;
    - a failed write.
  - `main.test.mts`: a run with no scope exits non-zero, with the usage message, before `protectHostGit()` or `ensureLabels()`; each round starts a fresh queue cache before the sweep.
  - Review fixes, each mutation-checked:
    - a <code>&#91;bot&#93;</code> host whose lookup says no is still the owner;
    - the round cache reads an unchanged issue once, and reads it again after a change, including a change to `updatedAt` alone;
    - a queue label differing only in case is kept;
    - a `sandcastle:ready` with no add event holds the issue without a write;
    - a CSV-breaking label is refused.
  - `follow-up.test.mts`, `intake.test.mts`, `umbrella.test.mts`: PR-level label restore, the split's scope label, and umbrella scope.
- **Operational note:** after this merges, every local `pnpm run sandcastle` needs `SANDCASTLE_ISSUE` or `SANDCASTLE_LABEL`. The chain walking to #147 is restarted with `SANDCASTLE_LABEL=Sandcastle`. The remaining queued issues (#147, #78, #79, #81) were all labelled by the owner's account, so they pass the new check.
